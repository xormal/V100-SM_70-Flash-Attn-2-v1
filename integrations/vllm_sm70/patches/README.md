# vLLM patches needed to run Qwen3.5/3.6 and Gemma-4 on `sm_70`

Patches against this 1Cat-vLLM fork, applied to `site-packages/vllm`. **Every one of them fixes a
defect whose only outward sign is a WRONG ANSWER** — the server boots and serves in all cases. That
is why each entry below records the *symptom* and the *evidence*, not just the change.

Apply from the site-packages `vllm/` directory:

```bash
cd <venv>/lib/python3.12/site-packages/vllm
patch -p0 < 01-qwen3_5-gptq-load.patch
patch -p0 < 02-gptq-modules-to-not-convert.patch
```
(The originals ship with CRLF line endings; the patches are generated with `--strip-trailing-cr`, and
applying them leaves the files LF. That is cosmetic.)

## 01 — `qwen3_5.py`: a quantised parameter with no output dim

`load_weights` splits a tuple-shard (`in_proj_qkvz` is fed by `in_proj_qkv` + `in_proj_z`) along
`param.output_dim`. GPTQ's `g_idx` is one value per **input** row, so it has no output dim and is
shared by every output shard — it must be loaded whole. Without this the load dies on
`AttributeError: 'RowvLLMParameter' object has no attribute 'output_dim'`, raised from inside a
`logger.debug()` argument, so it fails even with debug logging off.

## 02 — `gptq.py`: carry `modules_to_not_convert` through

The AWQ config exposes `modules_to_not_convert`; the GPTQ config dropped it. That attribute is not
used to decide what to quantise (`dynamic` does that) — but **models read it**.
`qwen3_5.py::_uses_split_gdn_input_projections()` asks whether `linear_attn.in_proj_a/b` were left in
fp16, and builds either SPLIT `in_proj_qkvz` + `in_proj_ba` modules, or one fused BF16-style
`in_proj_qkvz`. With the attribute absent, GPTQ always looked "unsplit", so the model expected a
single fused `in_proj_qkvz.weight` that a split quantised checkpoint does not contain. The only
outward sign was one warning line per GDN layer:

```
Parameter layers.N.linear_attn.in_proj_qkvz.weight not found in params_dict, skip loading
```

and then 47 of the 48 GDN layers ran on **uninitialised** weights.

## Checkpoint side

The checkpoint's `quantization_config` must carry BOTH:
* `dynamic` with `-:<regex>` skips naming the **fused** module names as vLLM sees them
  (`self_attn.qkv_proj`, `linear_attn.in_proj_ba`) — naming the source modules (`q_proj`, `in_proj_a`)
  never matches, because vLLM fuses before asking whether a layer is quantised;
* `modules_to_not_convert` in the AWQ spelling (source module names), which is what patch 02 forwards
  to the model.

See `../quantize/` for the converter.

## 03 — `v1/attention/backends/flash_attn_v100.py`: int8-склад ТОЛЬКО там, где внимание наше

`do_kv_cache_update` направляет запись в наш CUDA-склад по одному условию — `kv_cache_dtype`
начинается с `fp8`. А вот **внимание** идёт по нашему пути по ДРУГОМУ, более узкому условию:
`_supports_flash_v100_path()` требует, среди прочего, `sliding_window == (-1, -1)`.

Пока модель без скользящего окна (Qwen3.5/3.6) условия совпадают и разницы нет. На **Gemma-4** они
расходятся: 40 слоёв из 48 — скользящие, их внимание откатывается на Triton, а склад по-прежнему наш.
При `FA2SM70_KV_I8=1` это означает, что в 40 слоёв лягут **int8-байты с масштабом на позицию**, а
прочитает их Triton **как e4m3**. Симптом — не «чуть хуже точность», а мусор на выходе, причём
модель поднимется и будет отвечать.

Патч передаёт складу `allow_i8=self._supports_flash_v100_path()`. Тогда int8 стоит ровно там, где все
читатели наши, а слои со скользящим окном остаются e4m3 — их и пишет наше же ядро, потому что Triton
на Volta e4m3 не умеет писать вовсе. Пул при этом СМЕШАННЫЙ, и это уже поддержано: шим отмечает
формат на каждый кэш (`_FMT[ck]`), а сборка, префилл и декод читают именно отметку.

Правило, которое стоит за патчем: **приватный формат законен ровно до тех пор, пока каждый его
читатель наш.** Появился один чужой — формат обязан вернуться к общему.

## 05 — mamba/align: НЕ брать блок, закэшированный ДРУГОЙ заявкой В ТОМ ЖЕ ШАГЕ

Чинит боевой отказ «забор из восклицаний»: ответ на 100% состоит из `!` (токен 0) на всю длину
`max_tokens`, с первого же токена и без восстановления. Захвачено 6 случаев на боевом за день.

**Регистр.** У гибридной модели (16 слоёв внимания + 48 gated-delta-net) префикс-кэш принудительно
идёт в режиме `align`: `Qwen3_5ForConditionalGeneration` не объявляет `supports_mamba_prefix_caching`,
поэтому и `--mamba-cache-mode none`, и `all` схлопываются в `align`
(`model_executor/models/config.py`), а апстрим печатает про него EXPERIMENTAL. Отключить режим
через флаг НЕЛЬЗЯ — только вместе с префикс-кэшем.

**Корень.** Блок публикуется в хэш-карту префикс-кэша в `KVCacheManager.allocate_slots` —
то есть в `schedule()`, ДО `execute_model`, на токены, которые ещё не посчитаны. Для внимания это
безопасно: внутри слоя `reshape_and_cache` пишет KV всей партии до того, как ядро внимания её читает.
Для mamba — нет: рекуррентное состояние пишется только по итогам прохода, а читается ДО прохода
(`gpu_model_runner` -> `mamba_utils.preprocess_mamba`, индекс `(num_computed_tokens-1)//block_size`).
Значит вторая заявка с тем же префиксом, попавшая в тот же шаг планировщика, копирует себе
состояние из блока, который первая только что опубликовала и ещё НЕ заполнила. Внимание у неё
корректное, а состояние 48 слоёв — чужой мусор.

Межшаговый вариант этой же гонки апстрим уже закрыл (при `mamba_cache_mode != "none"` принудительно
выключается async scheduling, `config/vllm.py`). Внутришаговый — не закрыт.

**Лечение** (взято из более новой ветки vLLM, `1Cat-vLLM-fa2-work`,
`v1/core/single_type_kv_cache_manager.py`): `MambaManager` помнит хэши блоков, закэшированных в
текущем шаге, и если попадание опирается на такой блок — возвращает `num_gpu_blocks + 1` из
`get_num_blocks_to_allocate`. Планировщик считает, что места нет, и берёт заявку СЛЕДУЮЩИМ шагом,
когда состояние уже записано. Патч добавляет хук `new_step_starts()` по цепочке
scheduler -> KVCacheManager -> coordinator -> типовые менеджеры, чтобы чистить учёт на каждом шаге.

**Замер (зеркало на картах 0-1, пара БАЙТ-В-БАЙТ одинаковых заявок одновременно, холодный кэш):**

| | было | стало |
|---|---|---|
| промпт из захвата 12:10 | 18/20 пар | **0/20** |
| промпт из захвата 14:31 | 18/20 пар | **0/20** |

Префикс-кэш продолжает работать: доля попаданий 64.5%, повтор заявки 11.8 с -> 1.3 с. То есть
исправление ОТКЛАДЫВАЕТ заявку на один шаг, а не отключает кэш.

Контроли, снятые до исправления (каждый — отдельный подъём, факт проверялся поведением, а не
баннером): у каждой заявки своя соль (общего префикса нет) 0/15; префикс-кэш выключен 0/15;
`--enforce-eager` 0/10; наш скан GDN выключен 5/15 (то есть дефект НЕ наш); плита gptq `fold`
выключена 10/20; `USE_SHIM=0` + fp16-пул, ни одного нашего ядра — 13/20 и 18/20. Последнее и
доказывает, что корень в vLLM, а не в наших ядрах.

## 06 — `config/vllm.py`: на sm_70 у ГИБРИДНОЙ сетки снять порождение кода inductor

Чинит дефект #145: гибридные Qwen3.6 (`linear_attention` + `full_attention`, 48+16 и 30+10) под
`backend="inductor"` отвечают **связным, но неверным** текстом. Ни отказа, ни падения, ни NaN —
на вопрос о столице Франции приходит `1999-2000)\n- **1999-2000**:`. Класс дефекта тот же, что у
патчей 02 и 03: **сетка врёт молча**, и поймать это можно только чтением ответа или сверкой с
чужим путём — `relL2` наших ядер при этом прекрасен (2e-4).

**Дело не в ядрах внимания.** При одинаковой компиляции FA2_SM70 и TRITON_ATTN выдают **побитово
один и тот же** мусор (токены `16, 24, 24, 24, 12, 17, ...`). Бэкенд внимания на результат не влияет.

**Дело именно в порождении кода, и это доказано снятием подмен по одной.** `backend="eager"` меняет
не одну вещь, а **четыре**, и на этом уже один раз обожглись (ложное обвинение своих ядер):

| что ещё меняет `backend=eager` | проверено | вердикт |
|---|---|---|
| `ir_op_priority`: `native` → `vllm_c` | inductor+`vllm_c` / eager+`native` | **не при чём** |
| `custom_ops`: `["none"]` → `["all"]` | inductor+`all` / eager+`none` | **не при чём** |
| `ir_enable_torch_wrap`: `True` → `False` | inductor+`False` | **не при чём** |
| собственно порождение кода | см. ниже | **причина** |

Прямое подтверждение: у **первого расходящегося куска графа** (`submod_2` — выходная проекция GDN,
пост-внимательная норма, MLP) в оба плеча вложены **побитово одинаковые входы**, а выходы разошлись
на **~100 %**. Это не накопление шума fp16, а неверный код.

**Что уже проверено и НЕ помогает** (чтобы следующий не ходил по кругу):
одновременное отключение 12 проходов inductor (`epilogue_fusion`, `combo_kernels`,
`split_reductions`, `allow_buffer_reuse`, `layout_optimization`, `comprehensive_padding`,
`shape_padding`, `pattern_matcher`, `reorder_for_locality`, `joint_graph_constant_folding`,
`permute_fusion`, `benchmark_combo_kernel`) — мусор побитово тот же; статические формы
(`compile_sizes`) — мусор другой, но мусор; `empty_like` → `zeros_like` для
`self_attention_output` — не помогает (подстановка яда `full_like(1234.0)` доказала, что
содержимое буфера никуда не течёт); `VLLM_SM70_ENABLE_DENSE_F16_FASTPATH=0` — не помогает.
**До одного узла внутри `submod_2` сузить не удалось** — это честная граница результата.

**Цена — замерена, а не оценена.** Qwen3.6-27B-AWQ, одна V100, TP=1, промпт 1024, выдача 128,
медиана 3 повторов: декод **11.16 → 7.16 ток/с (−36 %)**, префилл 0.966 → 0.992 с (в пределах
разброса). Лечение дорогое; оно стоит здесь потому, что альтернатива — молча неверный ответ.

**Почему патч, а не строка в пускаче.** В пускаче её забудут при следующем переносе, и сетка снова
начнёт врать молча. Здесь это механизм: он привязан к признаку (`sm70` + `model_config.is_hybrid`) и
стоит **до** того, как `custom_ops` и `ir_enable_torch_wrap` выводятся из `backend`, поэтому все
четыре пункта переключаются согласованно. Аварийный выход:
`VLLM_SM70_ALLOW_INDUCTOR_ON_HYBRID=1`.

**Границы.** Замерено на двух гибридных Qwen3.6. Негибридные сетки патч не трогает: `Gemma4` не
наследует `IsHybrid`, `Qwen3_5ForConditionalGeneration` — наследует. Gemma-4 гасит порождение кода
своим пускачом, по своему замеру.

**Чем проверить:** сетка поднимается, в журнале строка
`SM70 + hybrid model: forcing compilation backend 'inductor' -> 'eager'`, и ответ на
«What is the capital of France?» осмысленный, а не `1999-2000`.

## 07 — `model_executor/layers/fla/ops/utils.py`: декоратор `input_guard` под обходом графа

Две независимые правки в одном декораторе, обе — про обход графа dynamo:

* `contiguous_args` собирался **генератором**, а генератор одноразовый. При обычном вызове это
  сходит с рук (распаковывается ровно один раз), под обходом графа тот же вызов обходится
  повторно и получает **пусто**;
* `torch.accelerator.device_index(...)` dynamo обойти не умеет: при `backend="eager"` обход падает
  прямо на этой строке, при inductor уходит в разрыв графа. В воркере vLLM карта уже выбрана и одна
  на процесс, поэтому под компиляцией контекст — тождественная операция.

**Дефект #145 этот патч НЕ лечит**, и это записано внутри самого патча. Проверено замером: патч
стоял в дереве во всех прогонах с включённым inductor (в том числе `custom_ops=all`, который до
него вообще не обходился), и гибридная сетка во всех них выдавала побитово тот же мусор.
Лечит #145 патч `06`.

## 09 — `csrc/quantization/awq/awq_sm70_gemm.cu`: таблица памяти отвечала ЗА ЧУЖОЙ ВЕС

**Патч по исходнику C++/CUDA, а не по `site-packages`** (как и 08 наряда #92). Он ложится в
дерево vLLM и требует пересборки `_C.abi3.so`; `patch -p0` из корня дерева. В рабочем дереве
`1Cat-vLLM-fa2-work` тот же файл лежит по другому пути (`csrc/sm70_turbomind/ops/`), и правка там
уже применена — содержимое сверено с патчем посимвольно.

`sm70_f16_prepare` запоминает преобразованный вес в глобальной таблице, ключ которой —
**сырой `TensorImpl*` исходного веса, которым таблица не владеет**. Освободили вес — `malloc`
отдал тот же слот следующему тензору той же формы — и таблица вернула запись ПРЕДЫДУЩЕГО веса.
Наружу это выглядело как `relL2 = √2` (ответ, не связанный с правильным) при **тех же** `k_ld` и
форме, и лечилось подготовкой клона; отказ «плавал», потому что зависел не от порядка вызовов, а
от раскладки кучи.

Диагноз — **замером, а не рассуждением**: в каждой отказавшей точке возвращённый `tm_weight`
побитово равен преобразованию веса из `rep0/M1` либо `rep0/M8`, а адрес буфера чередуется ровно
между этими двумя записями (`EV_sm70f16_defect.md`, таблица «чей это вес»).

Правка: запись держит **слабую** ссылку на исходный `TensorImpl`. Слабая ссылка не даёт удалить
сам объект (~200 Б; хранилище освобождается как и раньше), поэтому адрес физически не может быть
переиздан, а `expired()` честно сообщает, что исходный вес умер — такая запись выбрасывается.
Дополнительно сверяется `data_ptr` — на случай `param.data = other`.

Тем же патчем закрыты два спутника того же класса:

* `sm70_f16_prepare` **принимал** N не кратное 32 (`linear_attn.in_proj_ba` при TP=2, N=48) —
  `PackingImpl<HMMA_884, OPERAND_B, 1, kRowMajor>` считает `n/32` целочисленно, то есть хвостовые
  строки теряются. Проверка стояла у вызывающего (`process_weights_after_loading`), а не в
  операторе. Теперь — в операторе, а гранулярность 32 выведена из тех же шаблонов, что
  инстанцирует конвертер, и закреплена `static_assert`.
* `sm70_f16_gemm_out` не сигналил ничем: брал упакованный вес и его `k_ld` на веру. Теперь
  отвергает `N%32`, `K%16`, `k_ld != 32*K` (для этого конвертера ведущая размерность упакованного
  веса всегда `32*K`), разные устройства и неплотный вес. **Содержимое** уже упакованного веса на
  этой границе непроверяемо в принципе — оно не несёт признака происхождения; этот класс закрыт в
  корне, в таблице памяти, а не здесь.

Устройство не тронуто: SASS всех семи ядер файла побитово совпадает с исходным.

**Чем проверить:** `tests/kernels/quantization/test_sm70_f16_prepare_identity.py` (10 случаев,
каждый в своём процессе; `FA2SM70_C_SO` выбирает проверяемый `.so`). На отгруженном бинаре —
8 отказов из 10, с патчем — 0 из 10, и 0 из 10 в трёх других порядках вызовов. Исходный
воспроизводитель `raw/EV_shapes/repro_sm70_f16_wrong.py` без единой правки: было 15/21 + 7/7 +
принял N=48, стало 0/21 + 0/7 + отказал.

## 08 — `q_gemm.cu`: свёртка обнулений GPTQ и **инвариант прохода** (задача #92)

Отличается от остальных: это не правка чужого файла, а **наш механизм целиком** (в ванильном
vLLM его нет). Патч приложен, потому что при переезде на другой форк его надо нести вместе с
инвариантом, а не одной оптимизацией.

**Что делает.** 236 ядер-заливок C на декодный токен заменяются ОДНИМ узлом `cudaMemsetAsync`:
выходы декодных умножений берутся из постоянной плиты. Замерено на стенде, воспроизводящем
боевую раскладку токена (236 умножений, 11.38 ГБ весов, V100): **15.357 → 14.898 мс/токен**
при B=1, то есть −0.46 мс, при потолке («не обнулять вовсе») 14.878 — взято 95 % потолка.

**Мина, ради которой патч и оформлен.** Механизм верен, только если на КАЖДЫЙ проход (токен)
приходится ровно один узел обнуления. Единица здесь — **проход**, и она не совпадает ни с
флагом «мы внутри захвата», ни с id захваченного графа. Обе ошибки замерены, обе молчат:

| граница прохода | что происходит | признак |
|---|---|---|
| по флагу (было отгружено) | два графа, захваченных подряд, сливаются; второй без обнуления | относительная ошибка **1.0** на втором воспроизведении, **2.0** на третьем, **падения нет** |
| по id захвата | при `full_and_piecewise` один проход = десятки графов, обнуление в каждом | **+1.06 мс/токен** и ошибка **1.65**: обнуление куска затирает выходы предыдущих кусков ТОГО ЖЕ прохода |
| по проходу (патч) | эталонная последовательность ширин `n`; проход закрывается на своём E-м умножении | — |

Нарушение инварианта — **ОТКАЗ**, а не тихий откат. Первый проход только наблюдается (слоты не
выдаются), поэтому обучение не может испортить числа.

**Вторая мина:** плита не была привязана к карте. Вызов с другой карты в том же процессе
(черновая модель спекулятивного декода) сворачивался по чужому указателю — воспроизведено:
**SIGSEGV**. Стало: откат на обычный путь, счётчик и одна строка в лог.

**Переменные:** `VLLM_GPTQ_ZERO_C=fold|1|never|0`, `VLLM_GPTQ_FOLD_EXPECT=236` (закрепить длину
прохода — включает жёсткий инвариант с первого прохода), `VLLM_GPTQ_FOLD_MB=40`,
`VLLM_GPTQ_FOLD_ZERO_ALL=1` и `VLLM_GPTQ_FOLD_LEGACY=1|check|graph` — фальсификаторы, все три
границы живут в одном бинарнике, поэтому «до» и «после» не различаются сборкой.

**Чем проверить:** внешний `probe92.py` (`PROBE=multigraph|pieces|device|count`) — шесть проверок,
из них три обязаны ОТКАЗАТЬ на дефектной границе и пройти на исправленной. Полный разбор и
измерения находятся во внешнем отчёте о валидации.
